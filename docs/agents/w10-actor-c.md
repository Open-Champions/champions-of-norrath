# Spell, skill and actor virtuals: AutoObject to Chest

Package `w10-actor-c`, branch `agents/w10-actor-c`, based on the shared reconstruction draft at `cc78a45e`. The brief named 33 symbols (listed under "Imports closed"); all 33 were unresolved imports of the partial build at that base (`unresolved-imports.json` of the wave-10 baseline build). Addresses and sizes below are symbol values of the private reference `work/private/SLUS_205.65`, taken with the EE `nm`; the bodies were read with the EE `objdump`. No game bytes, tables, listings or decompiler output are committed. The few strings and constants quoted are values the code uses.

Each function is its own commit, compiled with the reviewed EE `g++` `authored_cpp` flags, and has a `host_check.cpp` that exits non-zero when a call, argument, order, store, compare or constant is wrong. The host checks are not build inputs. Checks that dereference 32-bit pointer words or call through the object's vtable (about half of them) must be built with `-DNORRATH_W10AC_HOST`, which makes the source map pointer words to host addresses as offsets from `norrath_w10ac_host_base`; the EE build uses the words as addresses directly (the same idea as `w8avb`). Example: `c++ -std=c++17 -O1 -ffp-contract=off -DNORRATH_W10AC_HOST host_check.cpp msg_run.cpp`.

## Method and evidence

- **Observed (instruction reading):** every function was read in the EE disassembly and its jump tables and small-data float pool entries were read from the image. Float constants are reproduced bit-for-bit (for example `0.2f` is the pool value `0x3e4ccccc`; `2.917963981628418f` is spelled with enough digits to round-trip).
- **Observed (execution of the original):** for the larger functions I ran a private R5900 interpreter harness (outside git; it loads the private image) that executes the original function and the freshly compiled authored function from identical memory snapshots with identical stub callees, and compares every call and its arguments (including memory the arguments point to), the final memory outside the stack, and for the clones a digest of the new object at every constructor call. Results are quoted per function below. Coverage of the original's instruction words was recorded; the words never reached were padding nops, or (for `msg_run__10BlackWidow`) the dead search path of an inlined slot lookup over a freshly built, all-empty descriptor. That harness and its outputs are private and are not published. Roughly: Catapult draw 80 scenarios, Catapult run 400, Catapult hurt 500, both `setState` bodies about 1,000 each, Badger run about 12,000, BlackWidow run about 44,000 (three seeds), both clones 6 each (patterned sources, digest at every constructor call).
- **Observed (clone ranges):** the copied byte ranges and the interleaving of constructor calls in the two Creature-derived clones were established by running the original clone on a patterned source and comparing the result, not by transcribing each load/store; the authored code copies those ranges with `copy_bytes` (as the existing Creature clone source does).
- **Host-check strength:** every host check was run against hand-made mutants (changed numeric literals; roughly 200 to 300 per group). Survivors are listed under "Authored but never executed"; they are either equivalent (a later store overwrites the byte, or a shifted nonzero test) or concern code that only compiles for the EE (the inline `rsqrt.s`).
- Nothing here ran on an EE or in the original process. Compiled bodies are larger or smaller than the image extents (behaviour reconstructions, not byte matches); no byte match is claimed.

## Authored but never executed

All 31 units compile with the reviewed EE `g++` `authored_cpp` profile. None ran on the EE, in the original process or as gameplay. What was compared:

- Host checks (all units): call order, arguments, stored bytes, flag gates, null/zero/boundary values, including signed/unsigned comparisons and 16-bit wraparound, scripted so that each branch is taken.
- Paired runs against the image (private, described above) for: `msg_draw__8Catapult`, `msg_run__8Catapult`, `msg_hurt__8CatapultfP10GameObjecti`, both `setState` functions, `msg_run__6Badger`, `msg_run__10BlackWidow`, `clone__6Badger`, `clone__10BlackWidow`. The other units were checked by reading plus the host check only.
- Mutation survivors of the host checks (hand-made literal mutants): constants inside the `rsqrt.s` inline-asm helper (EE-only, not compiled for the host); array sizes of locals; stores that a later store overwrites (for example a copy range that runs one byte into the vtable word or a list-head word the next call zeroes); shifted-byte mutants of the little-endian word readers whose test values have no high bytes; a dead store of a vector component in `msg_hurt__8Catapult`.
- Floating-point: the single-precision operations follow the original's operand order (for example sums of squares as `x*x + y*y + z*z`, doubling as `x + x`), but R5900 NaN/denormal/rounding behaviour on the EE is not established; the host runs use IEEE binary32. `rsqrt.s` is an inline instruction, as in the lighting sources.
- Inlined library code: the 17-way `switch` statements compile with their own jump tables, not the image's. The inline slot lookup in `msg_run__10BlackWidow` (state 15) is written as a loop over four slots; at run time it always picks the first slot.
