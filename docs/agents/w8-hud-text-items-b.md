## Evidence

Addresses are from the pinned `SLUS_205.65` symbol table. Observed (read from the instructions or initial bytes), inferred (reasoned from several observations) and unknown are kept separate in the source comments. Static object names below are the ELF symbol names, which have size 0 for many of them.

- `fontRestrict__Fi` (0x001743a8, 32 bytes): argument -1 stores 100000 in `restrictChars`, anything else is stored as is.
- `fontStringSizeu__FP4FontPUsi` (0x001744a0) and `fontPrintu__FiiPUsi` (0x001744b8): forward their arguments to `_fontStringSizeu__FP4FontPUsi` and `_fontPrintu__FiiPUsi`. `fontPrint__FiiPci` (0x001743c8) widens the text with `ustrcpy__FPUsPc` into a 1024-halfword stack buffer and calls `fontPrintu`. `fontPrintCentered__FiiPci` (0x00174420) and `fontPrintCenteredu__FiiPUsi` (0x00174548) subtract half of the measured width (arithmetic shift) from x and call the underscore printer directly. Inferred: the last argument is a character count (`fontPrintWrapu` passes counts there); it was first called a colour in early commits and renamed.
- `fontPrintWrapu__FiiPUsiiii` (0x00173c08, 632 bytes): word-wrapping loop over `_fontStringSizeu`, with `language == 5` meaning one character per segment, a newline adding 1000000 to the carry, `restrictChars` limiting the printed total and `fontLastPrintedPosition` recording it.
- `fontStart__FP4FontiUii` (0x00172bc8), `fontScissor__Fiiii` (0x00172e88) and `fontEnd__Fv` (0x00172f88) build a packet at `glistp`: an 8-byte DMA tag slot, the word 0x11000000, padding so the 0x50000000 word sits at 12 mod 16, a GIF-tag-shaped header with seven register/data pairs, and a second tag whose loop count and the 16-bit counts are patched at the end. The register numbers (0x3f, 6, 0x14, 1, 0x42, 0, 0x47, 0x40) and the values stored with them are observed; the GS register names for them are only inferred from the numbers and are not claimed in the source. `fontEnd` queues the packet through `drawAddToList__FPviP8_textureP11_drawRecordi` unless `coreLoadingScreenRunning` is nonzero.
- `hudShowMsg__FPUsN20iii` (0x001c6788, 708 bytes): layout from the measuring calls to `fontPrintWrapCenteredu__FiiPUsiiii`, the three colour constants 0x1e6464, 0x323c3c, 0x3c4646 (alpha in the top byte), and the border drawn through `textureDrawBorder__FiiiiiUiPcii`.
- `hudFadeScreen__Fi` (0x001c7db8) clamps `fadeDownVal` to 0..128 and draws a full-screen rectangle; `hudResetFadeScreen__Fi` (0x001c7da0) sets it to 0 or 128; `hudClearInfoMessage__Fv` (0x001c7688) clears the timer halfword.
- `msgHudRecall__Fc` (0x001c7900) sends {3, byte}; `msgHudPlayerExit__Fv` (0x001c7970) sends {5, first local player index or `nmPlayers`} when the network mode is nonzero and there are at least two players.
- `hudKick__Fv` (0x001c8008), `inventoryReset__Fv` (0x001b1808), `inventoryInit__Fv` (0x001b0508), `hudFinishGold__Fv` (0x001c44f8), `hudAssignQuickSpell__Fiii` (0x001c7a00), `hudAssignSpellBookSpell__Fiiil` (0x001c5de0), `getWeight__4itemPQ24item11description` (0x001080d8), `invShutDown__Fi` (0x001b1358) and `picProcess__4itemv` (0x001005a8): offsets and ordering are written out in each source comment. Player records are 23984 bytes apart at `player` (0x00408600); the inventory table is 4 records of 116 bytes at 0x00427288; the picture records are 64 records of 192 bytes at `_4item$picList` (0x004d7080) and the picture buffer is 256 slots of 1280 bytes (0x00487080).
- Data: `infoMessage` (0x007d0798, extent limited to 200 bytes by the next symbol, so 100 halfwords is an upper bound and the capacity is inferred), `infoMessageTimer`, `infoMessageAlways`, `hudFooterUni` (256 zero bytes) and `fontLastPrintedPosition`. All hold zero in the image, so this compiler placed them in the uninitialized region.

## Authored but never executed

All 25 functions and the five data objects above. In particular the packet writers `fontStart__FP4FontiUii`, `fontScissor__Fiiii` and `fontEnd__Fv` were checked only by reading back the bytes they write in a host buffer.
