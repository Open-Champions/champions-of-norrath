# w16-io-b: memory card, file, string table, ESF parse and sound device (part 2)

Package notes for `agents/w16-io-b`. All 21 owned symbols are authored, one per commit, under `experimental/sources/w16-io-b-*/` (a `.cpp` plus a `host_contract.cpp` each). Per-function observations (addresses, sizes, control flow) are Observed/Inferred/Unknown comments at the top of each source. Pushed after every commit.

## Checks performed

- Each unit compiles with the reviewed EE g++ under the unchanged `authored_cpp` flags (checked against the flag list in `experimental/build-plan.json`). Compiled body sizes are in the plan entries below. I did not run a full partial build (one private object per unit only), so link-level effects are unchecked.
- Each `host_contract.cpp` builds and exits 0 with the host C++ compiler (21 of 21), with mocked callees that check call order, arguments and return values.
- Each function was run side by side with the original in a private R5900 interpreter harness (kept outside git): same memory snapshot, same hooked callees, comparing return value, call log and every changed byte outside the stack. Scenario counts: IsPrepared 1, ProductId 2, SetRepeat 3, Format 15, SetMcSessionId 6, IsMcSameSession 1, AsyncIdle 901, WriteFile 30, PadAsync 291, Prepare 88, VICdSearchFile 36, ResetState 1, Read(signed char) 108, Read(unsigned long) 108, ReadStringLength 108, ReadStringBody 1120, ReadBegin(offset) 96, ParseZoneRoomActorsObj 70, ParseZoneRoomStaticLightingsObj 70, ParseZoneResource 507, ProcessRawFile 396. All reported zero mismatches and no halted runs.
- Each non-trivial function was also mutation checked: a changed constant, comparison or offset in a copy of the source made the paired run report mismatches (examples: a zero-extending store in `VISetMcSessionId`, the `n/2 + 2` term in `VIMemCardPadAsync`, the -2/-5 results in `VIMemCardPrepare`, the byte swap and BOM tests in `ProcessRawFile`). One mutation (`words[1] > 1` for `words[1] != 0` in `ParseZoneResource`) is equivalent for the scenarios used and was not caught.
- `python3 -m unittest discover -s tools -p 'test_*.py'`: 214 tests pass.

## Authored but never executed

All of it in the game sense: nothing has run on hardware or inside the game. The paired runs use a private interpreter with hooked callees, so they show equivalence of the call sequence and memory effects for the scenarios tried, not the behaviour of the callees. Specifically unexecuted: the memory-card calls against a real card or the SDK library (every `sceMc*` call was a hook returning scripted values, so what the result codes -2, -3, -5, -9 mean to the SDK is not verified); the `VIMemCardPrepare` body past its first check, because `VIMemCardIsPrepared` always returns 1 in this image and a real call stops after the status check; the `ProcessRawFile` conversion helpers (`UTF8_strlen`, `UTF8_convertToUTF16`, `str8to16`), all hooks; `ParseZoneResource` callee parsers, all hooks; the progress callback stored at parse +4 (called through a hooked fixed address); `VICdSearchFile` against the IOP.

## Unknown

- Member names throughout; the true layout of `VIObjFile` (only offsets 232, 240..., 560..588 used here), `VIESFParse` (offsets 4, 8, 12, 28, 36), the zone room record (120-byte rooms, arrays at +60/+68, table pointer at zone +96) and `VIXmi` (only the word at +52).
- The image's `long` is 64 bits wide (`Read__9VIObjFileRUl` reads 8 bytes, `VISetMcSessionId__FUl` stores a doubleword, `ReadBegin__9VIObjFileUlRUsT2` takes a 64-bit key), while the plan profile is `-mlong32`. The sources therefore use `unsigned long long` for the mangled `Ul` parameters; `VISetMcSessionId` stores the sign-extended register as the image does (a zero-extending store was the mutation caught). The note in `w16-io-b-mc-session-id` calls the width unknown; the other three functions now settle it as 64 bits.
- Why `VIMemCardIsPrepared` is constant, why `VIIsMcSameSession` ignores `sSessionId`, what `sAsyncMode` values 0 and 2 mean beyond "read in flight"/"pad write in flight", what the unit of the `VIMemCardPadAsync__Fi` argument is and why `count/2 + 2` is added, what the marker file written by `VIMemCardPrepare` is for, and what seek origin 0 means in `ReadStringBody`.
- Why the UTF-8 length mismatch in `ProcessRawFile` returns 1 while every other failure returns -1.
- What the flag word at parse +12 means in `ParseZoneResource`, and what `ParseZoneActor` / `ParseStaticLighting` return on success.
- Nothing here was byte-compared: matching is behavioural, the compiled sizes differ from the original (for example `VIMemCardPrepare` 968 bytes versus 912 in the image).
