# w11-actor-a: actor class methods (1 of 3)

Branch `agents/w11-actor-a`. Private executable `work/private/SLUS_205.65`; GP is `0x004879f0`. Addresses and sizes below are the image's own symbol table. Nothing here ran on the EE or inside the game.

## Method and checks performed

- Each function was disassembled privately (nothing derived is committed), rewritten as readable C++ and compiled alone with the reviewed `authored_cpp` flags (EE GCC 15.2.0, `-G0 -O2 ... -march=r5900 -std=c++17`). Every unit compiled. Authored bodies are not byte-identical to the image (sizes differ, table below); no byte-match claim is made.
- Every unit has a `host_check.cpp` built with the host C++ compiler (`c++ -std=c++17 -ffp-contract=off`, the float-heavy ones need that flag so the host does not fuse multiply-adds). Units that keep 32-bit pointers in game structures use the `W11_ACTOR_A_HOST` switch of `sources/w11-actor-a-common/access.hpp`, which keeps stored addresses as offsets in a test arena. The libc string functions used by the NPC and MissileWeapon sources are named through assembler labels (`libc_strcmp` ... `__asm__("strcmp")`) so a host check can bind them to wrappers. All 37 host checks exit 0 after the last commit.
- Private paired runs (outside git): a small R5900 interpreter (`priv-w11-actor-a`, derived from the wave-10 copies with the `sqrt.s`/`rsqrt.s`/`cvt.w.s` fixes and a halted run counted as a failure) loaded the original function and my freshly compiled one from the same memory snapshot with identical Python stub callees (hooks keyed by the original symbol names, fake table targets keyed by raw address) and compared the ordered call log (argument registers, float registers, the bytes behind pointer arguments, stack arguments, a hash of the object at each call) and every changed byte outside the stack. Scenario counts are in the commit messages and the table below; instruction coverage of the original was measured and the few words never executed are listed per function in the commit message (padding, annulled delay slots and the dead paths named under "Findings").
- Mutated copies were run through the same comparisons for every non-trivial function (changed constants, offsets, bit tests, loop counts, ranges). Each mutation was detected except two, both noted in the commit messages: a type-info comparison written `== 1` versus `!= 0` in MissileWeapon `msg_collision` (equivalent for a 0/1 result) and a one-ulp change to a float constant in AutoChest `spawnItems` (no scenario sat on an integer boundary). Mutations that first slipped through (a rare roll, a tie, a threshold) led to extra targeted scenarios.
- `python3 -m unittest discover -s tools -p 'test_*.py'`: 214 tests, OK, after the last source commit.
- I did not run `tools/build_partial.py` (the plan and snapshot are not mine to edit); the plan entries below come from compiling each unit alone with the reviewed flags.

## Findings worth knowing (observed unless marked)

- MissileWeapon `msg_run`, kind 5 (the 32-particle snow loop): the second unit-ball sampler is seeded from a stack word that is never written in the function (`lw a1,720(sp)`), and the final state is then stored into the object's random word at +68. The authored code reads an uninitialised local through an empty `asm` so it is as indeterminate as the image's; the paired runs fill the stack with a constant so both sides read the same value. Whether this is a defect of the original is inferred, not known.
- MissileWeapon `msg_run` rolls its own random numbers inline from the word at +68 (`s * 0x19660d + 0x3c6ef35f`, drawn as `s >> 16`) instead of calling `eRand`; `FireBomblet msg_run` and AutoChest `spawnItems` use `eRand__10GameObject` and the global `syncRandState`.
- Paths the image contains but cannot reach, kept in the sources for fidelity and named in the commit messages: the item-description slot search in FireBomblet `msg_run` (all four slots start empty, so the first slot is always taken); the colour reset for kinds 0 and 3 in MissileWeapon `msg_draw` (only kinds 2, 5 and 6 reach it); the 15PushPhysicsProp type check at the end of MissileWeapon `msg_collision` (the flag test before it already returned) and the `__throw_bad_typeid` after a null check of an object whose flags were just read. A null object in `msg_collision` makes the image read the word at address 12 before it notices; that read is not reproduced.
- Several image functions capture a value in a branch delay slot before the call that precedes it returns (FireBomblet `msg_run`, AutoChest `spawnItems`, MissileWeapon `msg_run`); each was checked against the paired logs. The Innoruuk `deathEffect` heading argument is truncated to a short inside the function (the image shifts it left and right by 16 itself), so it is declared as an int in the authored source.
- Four particle definitions are file-local objects with a name shared by another file-local object: `hitParticleDust2` (0x007d70c0 here, 0x007d69c0 elsewhere), `sparkParticle` (0x008d62d0 here, three others), `ballSparkParticle` (0x00600be0 here, 0x007d6330 elsewhere) and `snowParticle1` (0x00600c30 here, 0x007d5f70 elsewhere). The comparison treats the same-named objects as the same.
- Unnamed float constants are read through the global pointer or from `.sdata` and are written as bit patterns in the sources: 0x004811c8 (3.45, Cyclops `generateDust`); 0x00481030..0x00481040 (Innoruuk `deathEffect`); 0x00482594..0x004825a0 (FireBomblet `msg_run`); 0x0047fd28..0x0047fd30 (MissileWeapon `msg_draw`); 0x0047fd34 (`findClosestShadowBall`); 0x004806d0..0x004806dc (GutChunk `msg_run`); 0x004816f4..0x00481700 (`spawnItems`); 0x0047fd04..0x0047fd24 (MissileWeapon `msg_run`). The alpha tables at 0x004860d0 and 0x00483b78 and the colour table at 0x00462180 are written as literals.
- `initType__5Mummyb` is already authored and verified by the earlier unit `w9-rtti-vtables-entities-c-mummy-init-type`, but under the name `norrath_mummy_init_type` (the name the authored Mummy constructor imports). I did not duplicate it. Closing the original name needs an alias or a second symbol label in the plan; that is the integrator's decision, so it is not counted as closed here.
