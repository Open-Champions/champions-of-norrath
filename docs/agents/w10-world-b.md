## What was checked

- Every function: a `host_check.cpp` (host compiler, `-Wall`, floating-point code with `-ffp-contract=off`; exits non-zero on a wrong store, result, call order or branch; not a plan input). Where a pointer-sized field matters, the check uses an arena (`NORRATH_HOST_ARENA`) or documents that the host pointer is 8 bytes. The larger ones carry an independent model: `getFreeFrameState` (3000 random rings against a vector model), `generateSortedListAndInfoHeaders` (400 random directories against an insertion-sort model), `getClearradius` (all 76 names plus case/prefix/suffix variants against a model), `gameLineRayCollision` and `gameLineFuse` (hand-built cases for every threshold). Mutation spot checks (one deliberate change to the source, then a paired run that must fail) were done for `gameLineGetVert` (stride), `gameLineGetNextPoint` (step), `jumpGateLoad` (return value) and `hideHiddenObjects` (bit mask); all four were caught. Two expectations of mine in host checks were wrong and were corrected from the code's actual behaviour (the Skeleton `-1 + 1` base answer, and the NaN case in `gameLineRayCollision`: 0/0 passes both range tests, as the compare instructions do).
- Every function: a private paired run. A small R5900 interpreter (outside git, copied from the other packages and kept at `/Users/case/norrath-agents/priv-w10-world-b/`) loaded the private image, linked the authored object at a separate address with every undefined symbol bound to the original's address, and ran the original and the authored function from identical memory snapshots with identical Python stand-ins for callees. Return value (where one exists), the callee call log with arguments, and every changed byte outside the stack were compared. Scenario counts, all with zero mismatches and no halted run: `init__3mapi` 5, `gameLineGetVert` 60, `gameLineGetNextPoint` 60, `jumpGateSaveFootPrint` 1, `jumpGateLoad` 10, `hideHiddenObjects` 80, Demon `isEnemy` 200, Skeleton `isEnemy` 200, `getClosestLivingPlayer` 300, `getFreeFrameState` 600, `initPosition` (path state) 300, `initPosition` (two indices) 60, `isBoss` 400, `freeLump` 200, `initJumpEffect` 40, Wraith `isEnemy` 400, `gameLineRayCollision` 1500, `generateSortedListAndInfoHeaders` 300, `gameLineFuse` 400, `getClearradius` 527 names. Coverage of the original's instructions in these runs is listed below; every uncovered word was a padding nop, an annulled delay slot, or a path the image cannot reach.
  - `isEnemy__8Skeleton…` 59/60 (a nop); `getFreeFrameState` 50/53: the three misses are the "front node has a previous link" store pair, which is only reachable on an input that makes the image loop forever; `isBoss` 157/183: the six `__throw_bad_typeid` call sites (unreachable, the flag word is read first) and nops; `freeLump` 64/65 (nop); `isEnemy__6Wraith…` 107/108 (nop); `generateSortedListAndInfoHeaders` 147/148 (nop); `gameLineFuse` 246/253: the "line not found in the table" arms of the two removals, the null-second-line skip, and nops; `getClearradius` 471/477 (nops and annulled slots); `getClosestLivingPlayer` 55/55; `gameLineRayCollision` 179/179; both `initPosition` 60/60 and 80/80; `initJumpEffect` 48/48.
- Interpreter defects found and fixed in the private copy while doing this package (they affect any other private copy of the same code): `sqrt.s fd, ft` read the `fs` field, which is only right when the source register is `$f0`; the harness now also prints a `WARNING HALT` line (a halted original/authored pair used to count as a pass); `fargs` (float arguments) is applied; the image's `strcmp` appeared to stop the interpreter in the `gameLineFuse` setup (coverage ended at the call; the cause was not investigated), so it is stood in for by a Python hook in the `gameLineFuse` and sorted-list runs (`strcasecmp` and `strstr` likewise for `getClearradius`).

## Reading notes (observed / inferred / unknown, in brief)

- `getClearradius__FPCc` is an ordered chain of 76 compare calls plus an inline case-insensitive prefix test for names starting with "skeleton". The results were obtained by running the original with each compare forced to match and recording the return, and the order from the call sequence; the literals are the image's strings (identifier-like names). The unit is a large literal table; the order, not the individual values, is where it can go wrong, and the paired run checked 527 names (every literal plus case, prefix and suffix variants).
- `isEnemy__5Demon`, `isEnemy__8Skeleton` and `isBoss` compare the type returned by the object's first virtual-table slot (word +72, slot at byte 4, called with no argument) against `__tf<Name>()` through `__eq__C9type_infoRC9type_info`. That slot reading is inferred from the code shape; the existing `msg_run__7Trigger` note describes the same call as the table's first function, and whether the two descriptions name the same slot was not checked. The name of the slot is unknown.
- `isEnemy__8Skeleton` turns a nonzero base answer `r` into `r + 1`; this is as observed, not a typo. `isEnemy__6Wraith` also clears a rival Wraith's claim word (+576) and calls `listDestroy__FP8ListHead` on it when this Wraith is much closer to the target; the reading of +576 is inferred.
- `gameLineFuse__Fv` ends with a busy spin of `gameLineCount` iterations of six nops, as observed. A failed 24-byte allocation appends a null line pointer; the image's next scan reads through it (the same here).
- `getFreeFrameState__Fv` loops forever when the only node is busy (and when a busy front has a previous link), exactly as the image; no host test enters those cases.
- `initJumpEffect__Fv` takes its start vector from `worldCameraPos` (0x37ee80) and its end vector from `GetLastTarget__6Camera(&target, gameCam)` plus 90.0 in z; the +0.0 on x is observed and kept (it turns -0.0 into 0.0).
- `generateSortedListAndInfoHeaders__Fv` uses a local index list sized for 64 directory records (the image's size is unknown).
- `jumpGateSaveFootPrint__Fv` returns whatever `jumpGateSave__FPc` returned (484); the return type is inferred as `int` from the untouched result register.

## Not done

- `gameAttackResolver__FP10GameObjectT0ffiiiiPQ24item11descriptionb` (0x1ce218, 9184 bytes, ~2300 instructions) was inspected and not attempted: it is the attack-resolution core with soft-double arithmetic (`fptodp`, `dpadd`, `dptofp`, `litodp`, `fmod`), the linear-congruential roll, about 35 different callees (spell, skill, shield and flying-text constructors, sound lookups), and many field offsets of several classes whose layouts nothing in this package establishes. A faithful, paired-verified reconstruction would need the layouts of Creature, Player, the item description and several spell classes first. It stays unresolved.
- `gameStateData` is defined here as 8192 bytes (a recorded size is absent; the distance to the next symbol is used). The script-amx package already defines the same block as `norrath_script_game_state_data_view`, so the integrator should keep one of the two.
