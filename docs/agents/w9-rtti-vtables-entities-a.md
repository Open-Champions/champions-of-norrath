# w9-rtti-vtables-entities-a

RTTI, vtables and entity class methods (a). Branch `agents/w9-rtti-vtables-entities-a`. One verified function per commit; the 9 data views are one commit each. Every source was compiled with the reviewed `authored_cpp` flags and EE g++, has a host check beside it (`host_check.cpp` / `host_test.cpp`, not plan inputs, they use the host C library and stubs) and was also compared against the original function in a private R5900 interpreter (outside git, loads the private `SLUS_205.65`; see below). Addresses are from the private image whose hash is the snapshot `target_sha256`. Compiled sizes are `st_size` from the EE compile and are not original-byte matches.

## Verification performed

- Each unit compiled alone, and all 44 together in a full private partial build (plan and snapshot copies kept outside git, made with `docs/agents/w9-rtti-vtables-entities-a-plan-entries.py --private-root`): 2360 compilations, one relocatable link, 1911 function bodies, 1487 unresolved imports, COMMON zero. The same tree before these units gives 2316 inputs and 1511 imports. These counts are for this branch alone.
- Paired runs: the authored function and the original were run from identical memory snapshots in the private interpreter, with every undefined symbol bound to the original's address, identical stub callees (call logs include argument values and, where relevant, the floating registers) and a comparison of return value, call log and every changed byte outside the stack. Scenario counts per function range from 7 (type_info destructors) to 1359 (Goblin `initType`). Every function matched on all scenarios. Mutating one constant, index, flag test or copy range in each of seven units (the five user/single-inheritance RTTI routines, the 6Candle destructor, the 9DoorSwing clone) made the run fail, so the comparison does detect changes. Instruction coverage of the original was not measured.
- `python3 -m unittest discover -s tools -p 'test_*.py'`: 214 tests OK.
- Pushes: the `view-44ed78` commit and the ten destructor commits that follow it (`dtor-7blocker` through `dtor-11autochestlp`) were pushed together after the last of them, not one by one as asked; every other commit was pushed right after it was made. No pull request.

## Observed

- RTTI: the user-type slots (`do_upcast`, `do_dyncast`, `do_find_public_subobj` of `__user_type_info`) and the single-inheritance slots of `__si_type_info`. The single-inheritance routines forward to the base `type_info` held in word 2 of the object: base word 1 is its table, the slot is at table+16 (upcast), +24 (dyncast) or +32 (find), 8-byte entries of a halfword adjustment at +0 and a code address at +4, called with the base pointer plus the adjustment. All six compare type_infos through `__eq__C9type_infoRC9type_info`. The result records are four words (upcast uses three, dyncast four); word meanings other than "object pointer" and "access path" are not claimed. The constant 8 stored by the upcast match is unexplained.
- Destructors: ten with a vtable store at +72 (`7Blocker`, `7Candle2`, `6Candle`, `9DoorSwing`, `10DoorSecret`, `11FloorSwitch`, `7AntTrap`, `7EggSack`, `15AutoContainerLP`, `11AutoChestLP`), each calling one base destructor and freeing when flag bit 0 is set; `8AutoProp` (two vtable stores around `worldReleaseDoor`), `4Line` (frees the block at +20 whatever the flag), the three type_info destructors (they store `_vt$16__user_type_info` at +4, even `__si_type_info`, so a derived destructor installs the base-class table). `_$_10GameObject` is the function already authored as `norrath_vt_dtor_10GameObject`, compiled under the original's symbol (see below).
- Clones: copy ranges were taken from the load instructions of the original and confirmed by the paired runs. `clone__6Candle` embeds a copy of a 60-byte member at +76 followed by `lightAdd` when either of its first two words is nonzero; the class vtable is stored before the member copy.
- `initAttackVariant__5Demon`, `initAttackVariant__8Froglock`, `initType__13FemaleDarkElfb` and `initType__6Goblinb` share one "skill step": call slot 12 of the table at offset 96 of `skills[n]` with `(int)worldDifficulty`, scale by a single constant and an `eRand` roll (2^-16 scaled), and write a tagged 8-byte record into the first free (0xffff) or same-tagged entry of a four-entry array (at +1068 for Demon, Froglock, FemaleDarkElf; at +1100 for Goblin). Demon and the elves/Goblin add the scaled value to the base as an int; Froglock adds it as a float. The skill indexes, tags and constants per function are in the source comments.
- `msg_collision__13AutoContainerP10GameObject` follows the same shape as the PushPhysicsProp collision (rsqrt-normalised pair, push, then `objectAddToRunList`) with different guards; the push threshold is 52.0 and the factor is the single at 0x481710.
- `addTurnAnimation__3Cat` is a damped follower on the floats at +980/+984 driven by the halfword at +284.

## Inferred

- The third word of a single-inheritance `type_info` is its base, and word 1 the table pointer (from `__rtti_si` and the forwarded calls).
- `skills[13]` is `skillFireWeapons` in the image by symbol address, but no skill name is used in the sources; `skills[n]` names for 12, 14, 25 and 26 were not looked up.
- The 8-byte entries written by the skill step are records tagged 21..24 and 38; no name is claimed.
- Slot 12 of a skill's table returns an int used as a base value; nothing else is known.

## Unknown

- What the result record words, the constant 8, the tags, and the +156 byte values (1..8) mean.
- Which class owns `skills[12]`, `[13]`, `[14]`, `[25]`, `[26]` beyond the address of `skillFireWeapons`, and what slot 12 computes.
- The meaning of every constant single (0.2, 0.7, 0.8, 1.2, 1.4, 1.6, 0.52, 0.09, 0.6, 0.909, 2177, 52.0).
- `__tf9type_info`, `__tf10AutoObject`, `_$_10AutoObject` and the AutoObject virtuals, `_$_5Light`, `lightAdd__FP5Light`, `_$_10AutoPropLP`, `_$_13AutoContainer` (see opened imports) were not examined.
- Hardware behaviour (FPU rounding of `cvt.w.s` on the EE vs the interpreter's model, interrupt or fault behaviour) was not checked on real hardware or an emulator. The interpreter's single-precision arithmetic is the project's own and is the only evidence for the float scenarios.

## Authored but never executed

Nothing here ran on the EE, an emulator or in the game. The paired runs used a private interpreter written for this project, with Python stubs standing in for every callee (including `eRand`, the skill table call, `setParameters`, `lightAdd`, `objectRemoveString`, `listDestroy`, `blockFree`), so callee behaviour and the interaction between these routines and the real ones are untested. The paired-run scripts and the interpreter are not in the repository (they load the private executable), so the paired results can be reproduced only by someone who has the same private setup; the host checks in the repository are self-consistency checks of the stated behaviour with stub callees. The vtable views and constant words were produced from the image and are tested only by their host checks (slot order and names, and a compile) and by serving as the bound addresses in the paired runs.
