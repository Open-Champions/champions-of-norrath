# w11-vi-render-a

Package: VI renderer, scene and world (1 of 3). Branch `agents/w11-vi-render-a`. All source is under `experimental/sources/w11-vi-render-a-*`; each directory holds one authored function (or one constructor/destructor) and a `host_contract.cpp` next to it. The host contracts include host headers, so they are not EE plan inputs.

## How each function was checked

* Every unit was compiled with the reviewed EE g++ and the `authored_cpp` flags (direct compile of the single unit, kept outside the plan, because the official driver rejects a plan that differs from `snapshot.json`). All 31 units compile.
* Every unit has a host contract (`c++ -std=c++17`, linked x86_64 with statics below 4 GiB because the objects store 32-bit pointers). Each contract stubs the callees, checks the call order, arguments and stored values, and was run; the three functions authored in this session (`Render__16VIParticleSystemlR8VIRaster`, `GlobalInit__14VIEffectVolumeP7VIScene`, `Init__12VIAtmospherelR8VIRasteri`) were also run against a deliberately broken copy to confirm the contract fails.
* The three large functions were additionally compared with the original image in a private paired run (a small R5900 interpreter outside git that runs the original function and the freshly compiled authored function from identical memory with identical stubbed callees, comparing the call logs and every changed byte outside the stack). `Render` ran 10 scenarios with 320 of 320 original instruction words covered and no differences; `GlobalInit` ran 2 scenarios with 527 of 527 words covered and no differences; `Init` ran 14 scenarios (success, a hook-forced object count of 0, 1 and 3, each of the three allocation failures, a failure at each of the five CreateMaterial calls) with 709 of 711 words covered (the two missed words are the divide-by-zero trap instructions after constant divides) and no differences. No bytes of the image are in the repository.
* Fresh EE objects are not original-byte matches (for example the authored `Init` is 2,292 bytes against 2,844 in the image because the five material set-ups share one helper). Nothing here claims byte identity.

## Observed, inferred, unknown for the three functions of this session

The leading comment of each source file is the record (observed behaviour with offsets, inferred meaning, unknown). Summary:

* `Render__16VIParticleSystemlR8VIRaster` (0x010b8158, 1280 bytes): frame-time smoothing over an eight-float history (offsets 16..48), a walk of the emitter list at this+52 and, for each emitter with live particles, billboard batches (48-byte entries) with a colour-row lookup, a bounding box in the emitter, an optional attractor and recycling of aged particles to the list at this+64. Inferred: emitters/particles/free list. Unknown: member names.
* `GlobalInit__14VIEffectVolumeP7VIScene` (0x011466f8, 2108 bytes): stores the scene pointer and fills the image-named tables `sFogCard` (8 records), `sDustCard` (60) and `sFallEffect` (60) with 48-byte, four-vertex quads, each built through a zeroed local `VIMatrix44`. Unknown: what `Rotate*` do to existing matrix contents (the call sequence is reproduced exactly).
* `Init__12VIAtmospherelR8VIRasteri` (0x01066780, 2844 bytes): sets default parameters, allocates the 200 particle records, the 36-byte node block and the 32 x 2048-byte emitter block, fills sin/cos, rain, star and wave tables and creates five materials; returns -1 when one of the five CreateMaterial calls returns a negative id (the id is stored in its word first).
